## 2. Research-file errata found during cross-check (not app bugs — for Mary)

1. **age-calculator.md §4 Example 2, total_days off by one**: "8766 + 364 = 9130" — 2024-02-29 → 2025-02-28 is **365** days, so the correct totals are **9131** (at 2025-02-28) and **9132** (at 2025-03-01). The API's `total_days` (9131 / 9132, probe cases "age same-day" / "age") is **correct**; independently cross-verified against a third date pair (UI probe DOB 2000-02-29, today 2026-11-21 → 9762, hand-recomputed). The Y/M/D values in the example are correct and the engine matches them exactly.
2. **flames.md §4 Example 3, arithmetic slip**: "remaining = 3 + 6 = 8" — BOB(3) + MARCUS(6) = **9**; with n=9 the count-as-1 elimination yields **Enemy** (live API agrees), not the Affection concluded from n=8. The engine's Enemy here is consistent with the correct n.
3. **api-probe.json "moon-phase NM" expect line** says "waxing false", contradicting research moon-phase §3.4 (waxing = `D < 180` → **true** at D=0). The API's `waxing: true` is the research-correct convention; the expect line is miswritten.
4. **api-probe.json "moon-phase FM" expect line** ("next FM 2025-02-12T13:53Z") applies only if the query instant is *at* the FM instant; the probe queried 22:27:00 and the FM occurs 22:27:32, so the engine returning the same-day FM as "next" is defensible — but the semantics are undocumented (folded into QF-19).
5. **Task-brief note on moon_age ≈14.6 d**: the current research file does *not* carry 14.6/14.7 — Example 1 gives the mean-cycle estimate **14.22 d** and recommends measured Convention B; the engine's `moon_age_days: 14` (measured from actual prev NM 2024-12-30T22:27:25Z) conforms. No finding.

## 4. Top 5 issues for the cluster

1. **QF-01 (P0) — all four name-pair pages are dead.** One shared frontend bug (`name="name"` vs required `a=`) makes name-compatibility, love, friendship and flames unusable from the UI (400 on every submit). Highest blast radius for the least fix effort.
2. **QF-02 (P1) — FLAMES `remaining` undercount.** `tools.ts:233` reads the mutated `lb.length`, so every pair sharing ≥1 letter computes `n = true_n − removed` and can land on the wrong outcome — including the pinned Wikipedia regression vector Rohan+Lenna (Enemy instead of Marriage). Wrong for the *majority* of real inputs, not just edge cases.
3. **QF-03 (P1) — FLAMES negative-n garbage.** Identical (or subset) names produce negative `remaining`; the `=== 0` guard never fires and negative JS `%` + `splice(-k)` produce arbitrary-but-deterministic outcomes (Asha+Asha → "Marriage"). Needs the n=0 "perfect match" convention and a negative guard.
4. **QF-04 (P2) — moon-phase bins are centered, not half-open.** Up to ±5.6 h of mislabelled phase around every boundary, and a self-contradicting payload ("Full Moon" + `waxing:true`) on the FM day's default 12:00 UTC query; fails the research's own 2025-01-13T06:00Z edge vector.
5. **QF-06 + QF-07 (P2) — age has no input validation.** Impossible dates roll silently (Feb 30 → Mar 2, X4) and future DOB / end-before-DOB return negative ages with 200 OK — the only tool in this cluster without the `isCalendarDate` guard, and it also lacks research-mandated order checks.
